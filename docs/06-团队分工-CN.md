# TelecomSafe 团队分工方案

> 文档版本：v1.0 ｜ 生成日期：2026-08-19
> 英文对照版：[06-Teamwork-Allocation-EN.md](06-Teamwork-Allocation-EN.md)
> 团队规模：5 人（本文档使用占位标识 **成员 A–E**，团队确定后替换为真实姓名）

## 0. 使用说明

- 本文档中的 **成员 A–E** 为占位标识。第一次团队会议后，把姓名、联系方式填入 §2 的角色表即可。
- **队长（Team Leader）不预先指定**，由 §3 的提名标准与选举流程在首次会议上产生。
- 分工方案基于文档 `01-技术方案与里程碑-CN.md` 的五层架构与 M0–M7 里程碑；两份文档需同步更新。

## 1. 分工设计原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **按技术层切分，不按周次切分** | 每人拥有一个完整的技术层，端到端负责。避免"这周你做标注、下周他做标注"式的碎片化，责任不清 |
| 2 | **创新模块配双人** | L2 生成层是项目核心创新，单点故障风险太高，必须两人协作（主责 + 副责） |
| 3 | **每人都有一个 🔴 高风险任务** | 参照技术路线图 §5 的成熟度评估，高风险任务分散到不同成员，避免全压一人 |
| 4 | **接口先于实现** | 成员之间的数据格式、接口约定必须在编码前书面确定（见 §6），否则集成阶段必然返工 |
| 5 | **队长不承担最重的技术任务** | 队长需要 20–25% 的时间做协调、对接导师、管进度。若同时背最难的技术模块，两头都做不好 |

## 2. 角色定义与职责

### 2.1 角色总览

| 标识 | 角色 | 主责技术层 | 核心交付物 | 高风险任务 |
|------|------|----------|-----------|-----------|
| **成员 A** | 数据负责人<br>Data Lead | L2 数据 | Risk Taxonomy、标注规范、TelecomSeed 数据集 | 🔴 Risk Taxonomy 量化判据定义 |
| **成员 B** | 生成负责人<br>Generation Lead | L2 生成（主责）★ | LoRA 模型、四路生成引擎、TelecomSynth 数据集 | 🔴 生成质量达标（TG2） |
| **成员 C** | 感知负责人（人员）<br>Perception Lead – Workers | L3 Workers + Behaviour | Workers 多头模型、动作识别、E1–E3 实验 | 🔴 E3 增广有效性验证（TG3） |
| **成员 D** | 感知负责人（场景）<br>Perception Lead – Scene | L3 Machinery + Materials + Terrain | 三分支模型、地形分割、材料状态判定 | 🔴 地形/材料无公开数据 |
| **成员 E** | 融合与系统负责人<br>Fusion & System Lead | L4 融合 + L5 系统 | 规则库、三级融合、Web Demo、实验管理 | 🔴 三级融合无成熟先例（TG4） |

> ★ **成员 A 兼任 L2 生成的副责**。生成层是核心创新，A 与 B 需紧密协作：A 提供种子数据与规格库，B 负责生成与闸门。两人共同对 TG2 负责。

### 2.2 详细职责

#### 成员 A ｜ 数据负责人

**主要职责**
- 制定 **Risk Taxonomy**（4 大类 × 20–30 细类），为每个风险定义**可判定的量化标准**
- 编写标注规范文档，含边界情况判定规则
- 组织公开数据集下载、格式统一、类别映射
- 采集与筛选电信场景真实图像（目标 ≥500 张）
- 用 Grounding DINO 预标注 + 人工修正，产出 TelecomSeed-v1
- 维护 DVC 数据版本管理，记录每个子集的来源与许可
- **副责**：Stage 0 风险场景规格库（与 B 协作）

**关键交付**
| 交付物 | 截止 | 关联决策门 |
|--------|------|-----------|
| Risk Taxonomy v1.0 | W1 末 | TG1 |
| 标注规范文档 | W2 中 | — |
| TelecomSeed-v1（≥300 张已标注） | W3 末 | **TG1** |
| 数据划分与隔离方案 | W3 末 | — |
| Risk Taxonomy v2.0（含地形/材料细化） | W10 | — |

**为什么这个角色最先启动**：Risk Taxonomy 是关键路径的起点。标注、生成、评估三方都依赖它。A 在 W1 交付质量不高，后面所有人都会返工。

---

#### 成员 B ｜ 生成负责人 ★核心创新★

**主要职责**
- 基础生成模型选型对比（SDXL / SD3.5 / FLUX）
- LoRA 微调，注入电信施工领域视觉特征
- 实现四路生成引擎：T2I / ControlNet 布局控制 / Inpainting 局部编辑 / 背景替换
- 实现自动标注（布局图直转 / 掩码继承 / Grounding DINO + SAM 兜底）
- 实现并标定四道质量闸门（G1 语义 / G2 分布 / G3 标注 / G4 人工）
- 批量生成 TelecomSynth 数据集，产出质量评估报告
- 负责生成 pipeline 的消融实验 A1–A7

**关键交付**
| 交付物 | 截止 | 关联决策门 |
|--------|------|-----------|
| 基础模型选型报告 | W4 中 | — |
| LoRA 微调模型 | W4 末 | — |
| 四路生成引擎 | W5 末 | — |
| 四道质量闸门 + 阈值标定 | W6 中 | — |
| TelecomSynth-v1（≥3000 张）+ 质量报告 | W6 末 | **TG2** |
| Pipeline 消融实验 A1–A7 | W14 | — |

**风险提示**：这是全项目技术难度最高、也最容易延期的角色。建议 B 在 W4 就跑通一条最简链路（T2I → 10 张图 → 人工看），不要等四路全实现才验证。

---

#### 成员 C ｜ 感知负责人（人员维度）

**主要职责**
- Workers 分支：共享主干 + 多头结构（检测头 + 姿态头 + PPE 多标签头）
- Behaviour 分支：骨架动作识别（YOLOv11-pose → ST-GCN++）
- **执行 E1 / E2 / E3 核心对比实验** —— 项目成败的判定实验
- 合成/真实数据混合训练策略实现（配比调度、损失加权）
- 长尾类别专项实验 E6
- 鲁棒性实验 E7 的模型侧执行

**关键交付**
| 交付物 | 截止 | 关联决策门 |
|--------|------|-----------|
| Workers 检测 + PPE 基线（E1） | W7 末 | — |
| E2 传统增广对照 | W8 中 | — |
| **E3 生成增广实验结果** | W9 末 | **TG3** |
| 多头结构完整实现 | W10 | — |
| 行为识别模型（或 D6 降级方案） | W11 | — |
| E6 长尾实验 | W14 | — |

**风险提示**：C 的 E3 实验是全项目的判定点。建议 C 在 W7 就把 E1 baseline 跑通并冻结，之后所有对比都基于同一份 baseline，避免"基线一直在变"导致结论不可比。

---

#### 成员 D ｜ 感知负责人（场景维度）

**主要职责**
- Machinery 分支：检测 + 作业状态 + 人机距离计算
- Materials 分支：检测 + 堆叠几何规则（高宽比、越界、通道阻塞）
- Terrain 分支：语义分割（平整/坑洼/积水/沟槽/斜坡）
- 用 SAM 2 生成地面区域候选 + 人工归类，构建地形分割子集
- 与 A 协作定义材料"堆放不当"与地形"不平整"的量化判据
- 跨站点泛化实验 E9

**关键交付**
| 交付物 | 截止 | 关联决策门 |
|--------|------|-----------|
| Machinery 检测模型 | W8 末 | — |
| 地形分割子集（SAM 2 辅助标注） | W9 末 | — |
| Materials 状态判定规则 + 模型 | W10 末 | — |
| Terrain 分割模型 | W11 末 | — |
| E9 跨站点泛化实验 | W14 | — |

**风险提示**：D 负责的三个维度里，Terrain 与 Materials 都是 🔴 无公开数据、类别定义主观。**如果整体进度落后，D8 降级路径首先砍的就是这两块**。D 应在 W7 就与队长确认优先级：Machinery 必保，Terrain/Materials 可降级。

---

#### 成员 E ｜ 融合与系统负责人

**主要职责**
- 编码安全规则库（≥15 条可判定谓词，标注 OSHA / GB 26859 等法规出处）
- 实现实体图构建（人-机-料-地的空间关系建模）
- 实现三级分层融合（实体图 → 规则层 → 可学习融合）
- 组织专家风险等级标注（200 张，2–3 名标注者，计算一致性 Kappa）
- 系统集成：端到端 pipeline、FastAPI 后端、Gradio/React 前端
- 模型导出与加速（ONNX / TensorRT）
- 搭建并维护实验管理平台（W&B / MLflow）

**关键交付**
| 交付物 | 截止 | 关联决策门 |
|--------|------|-----------|
| 实验管理平台搭建 | W2 末 | — |
| 安全规则库 v1.0（≥15 条） | W10 中 | — |
| 专家风险标注集（200 张） | W10 末 | — |
| 三级融合模块 + E8 实验 | W11 末 | **TG4** |
| Web Demo 系统 | W13 末 | **TG5** |
| 端到端性能优化 | W14 | — |

**风险提示**：E 的两块工作（融合、系统）都在项目后半段，前期看似清闲。**建议 E 在 W2 就把实验管理平台搭好**（全队受益），并在 W8 提前启动专家标注的约人工作 —— 这件事最常被拖到最后导致 TG4 无法评估。

## 3. 队长（Team Leader）

### 3.1 队长职责

队长**不是**技术负责人，而是项目协调者。具体职责：

| 类别 | 职责 |
|------|------|
| **对外** | 与导师的唯一对接人；组织并主持每周线下例会；准备汇报材料 |
| **进度** | 维护看板；每周核对里程碑；识别延期并提前预警 |
| **决策** | 主持 TG1–TG5 决策门会议；组织降级路径的评估与表决 |
| **协调** | 处理成员之间的接口争议；调配临时人力支援落后模块 |
| **文档** | 保证会议纪要、决策记录、贡献记录及时入库 |
| **仲裁** | 技术分歧无法达成一致时组织表决；分工冲突时做最终裁定 |

**时间占比**：约 20–25% 用于协调工作，因此队长承担的技术模块应是五个角色中相对较轻的一个。

### 3.2 提名标准

候选人应满足以下条件。**加粗项为必要条件**，其余为加分项。

| # | 标准 | 说明 | 权重 |
|---|------|------|------|
| 1 | **能保证线下出勤** | 项目明确要求 `regular in-person meetings on campus`，且 `absence and remote working are unacceptable`。无法稳定到校者不具备候选资格 | **必要** |
| 2 | **时间投入可保证** | 项目要求 `substantial time commitment`；队长额外承担 20–25% 协调工作 | **必要** |
| 3 | **沟通与协调意愿** | 愿意主动追进度、处理分歧，而非只想埋头写代码 | **必要** |
| 4 | 项目管理经验 | 有带队或组织经验者优先 | 高 |
| 5 | 技术全局理解 | 能理解五个技术层的相互依赖，而非只懂自己那块 | 高 |
| 6 | 书面表达能力 | 需撰写汇报材料、会议纪要、与导师的书面沟通 | 中 |
| 7 | 冲突处理能力 | 能在分歧中保持中立并推动决策 | 中 |

> **重要提醒**：标准 1（线下出勤）是项目简介明文规定的硬性要求，措辞为 `absence and remote working on the project are unacceptable`。选举前请所有候选人先确认自己能满足这一条。

### 3.3 选举流程

在**第一次团队会议（M0，W1）**上完成：

```
Step 1  宣读职责与标准（5 分钟）
        全体成员阅读 §3.1 与 §3.2，确认理解

Step 2  自荐 / 他荐（10 分钟）
        · 自荐：有意愿者说明自己符合哪些标准
        · 他荐：可提名他人，被提名者需当场表态是否接受
        · 每位候选人陈述 2 分钟：为什么是我、我打算怎么管进度

Step 3  资格确认（5 分钟）
        逐一核对候选人是否满足三项必要条件（1/2/3）
        任一不满足者退出候选

Step 4  无记名投票（5 分钟）
        · 每人一票，可投给自己
        · 获票最多者当选
        · 平票：进行第二轮，仅在平票者之间投票
        · 第二轮仍平票：由导师裁定

Step 5  确认与记录（5 分钟）
        · 当选者当场确认接受
        · 记入会议纪要，更新本文档 §2.1 角色表
        · 同步告知导师
```

### 3.4 任期与更换

| 项 | 规定 |
|----|------|
| 任期 | 全项目周期（W1–W16） |
| 中期复核 | **W8（项目中点）做一次匿名满意度复核**，5 分制，低于 3.0 触发讨论 |
| 更换条件 | 满足以下任一：① 队长主动请辞；② 超过半数成员书面提出更换；③ 连续两周未履行核心职责（未组织例会、未维护看板） |
| 更换流程 | 重新执行 §3.3 的 Step 2–5 |
| 副队长 | 建议同时推选一名副队长（得票第二者），在队长缺席时代行职责 |

## 5. 工作量分布

### 5.1 按阶段的人力投入（每人每周小时数估算）

| 阶段 | 周次 | 队长* | A 数据 | B 生成 | C 感知-人 | D 感知-景 | E 融合系统 |
|------|------|-------|--------|--------|-----------|-----------|-----------|
| M0 立项 | W1 | 8 | **12** | 6 | 6 | 6 | 8 |
| M1 数据 | W2–W3 | 8 | **16** | 10 | 8 | 10 | 10 |
| M2 生成 | W4–W6 | 8 | 12 | **18** | 8 | 10 | 8 |
| M3 感知 | W7–W9 | 8 | 8 | 12 | **18** | **16** | 8 |
| M4 融合 | W10–W11 | 8 | 8 | 8 | 12 | **14** | **18** |
| M5 集成 | W12–W13 | 8 | 6 | 6 | 10 | 10 | **18** |
| M6 评估 | W14–W15 | 10 | 8 | 12 | **14** | 12 | 12 |
| M7 交付 | W16 | **14** | 10 | 10 | 10 | 10 | 10 |

\* 队长的工时为**协调工作**，需叠加在其本职技术角色之上。加粗为该阶段的主力。

**峰值提示**：
- **B 的峰值在 W4–W6**（生成 pipeline 全部工作压缩在三周），是全项目最紧张的时段
- **C 与 D 的峰值重叠在 W7–W9**，且此时 B 刚交付合成数据，容易出现"数据有问题→回退→感知等待"的连锁延期
- **E 的峰值在 W10–W13**，前期相对轻松，应主动承接前期的支援任务

### 5.2 前期人力再平衡建议

W1–W3 期间 A 的负载最重（Taxonomy + 标注规范 + 数据采集），而 C/D/E 相对空闲。建议：

- **C 与 D 在 W2–W3 支援标注工作**（每人 50–100 张），同时熟悉数据分布——这对后续训练调优有直接帮助
- **E 在 W2 搭好实验管理平台**，为全队后续实验做准备
- **数据采集是可并行的体力活**，建议全员参与拍摄/收集，A 负责筛选与标准把关

## 6. 成员间的接口约定

集成阶段返工的根源几乎都是接口没提前定。以下约定**必须在 W2 末书面确认**，任何变更需通知全部下游成员。

| 接口 | 上游 | 下游 | 约定内容 | 确认截止 |
|------|------|------|---------|---------|
| I1 | A | B, C, D | **数据格式**：COCO JSON；类别 ID 映射表；图像命名规范 | W2 末 |
| I2 | A | 全体 | **Risk Taxonomy**：类别层级、每类的量化判据、severity 取值 | W1 末 |
| I3 | A | B | **规格库 schema**：`risk_scenarios.yaml` 字段定义（见文档 03 Stage 0） | W3 末 |
| I4 | B | C, D | **合成数据交付格式**：与 I1 完全一致 + 元数据 JSON（seed/prompt/route/闸门分数） | W5 末 |
| I5 | C, D | E | **感知输出 schema**：统一的检测/分割/属性 JSON 结构，含置信度字段 | W6 末 |
| I6 | E | 全体 | **实验记录规范**：W&B 项目名、run 命名规则、必记指标清单 | W2 末 |
| I7 | A | E | **专家标注格式**：风险等级取值、标注者 ID、时间戳 | W8 末 |

> **I5 是最容易出问题的接口**。四个感知分支输出形态不同（框 / 掩码 / 多标签 / 动作类别），E 需要在 W6 就拿到统一 schema 才能设计融合模块。建议 C、D、E 三人在 W6 开一次专门的接口对齐会。

## 7. 协作机制

### 7.1 会议节奏

| 会议 | 频率 | 时长 | 形式 | 主持 | 产出 |
|------|------|------|------|------|------|
| **周例会** | 每周 1 次 | 60 分钟 | ⚠️ **必须线下（项目硬性要求）** | 队长 | 会议纪要入库 |
| 技术对齐会 | 按需 | 30–60 分钟 | 线下优先 | 发起人 | 决议记录 |
| **决策门会议** | 5 次（TG1–TG5） | 90 分钟 | ⚠️ **必须线下 + 导师参与** | 队长 | 决策记录 + 是否触发降级 |
| 日常同步 | 每日 | 异步 | 群消息 / Issue | — | 阻塞项当天暴露 |

**周例会固定议程**：
```
1. 上周完成情况对照（10 min）—— 逐人 2 分钟
2. 本周计划与依赖声明（15 min）—— 明确"我需要谁在什么时候给我什么"
3. 阻塞项与求助（15 min）
4. 里程碑与关键路径检查（10 min）—— 队长主持
5. 决议与行动项确认（10 min）—— 每项行动明确责任人与截止时间
```

> ⚠️ **关于线下要求**：项目简介明确写明 `regular in-person meetings and discussions on campus are required`，且 `absence and remote working on the project are unacceptable`。建议在第一次会议上固定每周会议的时间与地点，并全员确认可出席，写入会议纪要作为承诺记录。

### 7.2 代码协作规范

| 项 | 约定 |
|----|------|
| 仓库 | https://github.com/muamuauh/AY26S1-45-SPML |
| 分支策略 | `main` 保护；每人在 `feat/<模块名>` 分支开发；通过 PR 合入 |
| PR 规则 | 至少 1 人 Review；关联对应的 Issue；CI 通过（如已配置） |
| 提交规范 | `<type>: <描述>`，type ∈ {feat, fix, docs, exp, refactor, chore} |
| 大文件 | 数据与模型权重**不入 Git**，用 DVC 管理（`.gitignore` 已配置） |
| 实验记录 | 每次实验必须在 W&B 留痕，run 名含分支名与关键超参 |

### 7.3 升级机制（Escalation）

```
问题出现
   │
   ├─ 技术问题，自己 4 小时内无进展
   │     → 群里 @ 相关成员求助
   │
   ├─ 跨模块依赖阻塞，超过 1 天
   │     → 报告队长，队长协调优先级
   │
   ├─ 里程碑预计延期超过 3 天
   │     → 队长在周例会提出，全队评估是否触发降级路径
   │
   └─ 决策门未通过 / 成员长期缺席 / 无法解决的分歧
         → 队长上报导师
```

## 8. 贡献记录与公平性

小组项目最常见的矛盾是"贡献说不清"。建议从第一周就建立可追溯的记录，而不是等到最后互相举证。

| 记录方式 | 内容 | 维护者 |
|---------|------|--------|
| Git 提交历史 | 代码贡献，天然可追溯 | 自动 |
| PR 与 Review 记录 | 谁写的、谁审的 | 自动 |
| 会议纪要的行动项 | 每项任务的责任人与完成情况 | 队长 |
| 实验记录（W&B） | 谁跑了哪些实验 | 自动 |
| 文档章节署名 | 论文/报告每章的执笔人 | 队长汇总 |
| **月度贡献自述** | 每人 W4 / W8 / W12 / W16 各写一段 200 字工作小结 | 各成员 |

> **建议**：在最终报告中附一张**贡献声明表**（Contribution Statement），列明每人负责的模块与主要产出。这是学术论文的通行做法（CRediT taxonomy），也能有效避免评分争议。

## 9. 应急预案

| 情况 | 应对 |
|------|------|
| **某成员长期缺席（> 2 周）** | ① 队长先私下沟通了解原因 ② 无法恢复则上报导师 ③ 其职责按 §9 表重新分配 |
| **某成员进度严重落后** | 周例会公开评估；由队长调配临时支援；必要时缩减其模块范围 |
| **队长无法履职** | 副队长接管；按 §3.4 重新选举 |
| **关键成员（B）离队** | B 的生成模块由 A 接手（A 本就是副责）；同时触发降级路径 D2 简化生成路线 |
| **两人以上同时缺席** | 立即上报导师，重新评估项目范围（大概率触发 D8） |

### 成员缺失时的职责再分配预案

| 缺失成员 | 职责接管方案 | 触发的降级 |
|---------|------------|-----------|
| A（数据） | Taxonomy → 队长 + E；标注 → C、D 分摊；采集 → 全员 | 数据规模缩减，可能触发 D1 |
| B（生成） | 生成 → A 接手（副责）；闸门 → E | **D2**（只保留 Inpainting 路线） |
| C（感知-人） | Workers → D 接手；行为识别 → 直接放弃 | **D6**（单帧姿态替代） |
| D（感知-景） | Machinery → C 接手；Terrain/Materials → 放弃 | **D8**（降为两维） |
| E（融合系统） | 融合 → 队长 + C；系统 → 简化为脚本 | **D4 + D5** |

> 这张表的意义不是"预期有人会走"，而是让团队清楚：**每个角色的不可替代性有多高**。B 和 E 的缺失代价最大，因此这两个角色更需要有人能"看得懂"其代码——建议 PR Review 时刻意让另一人审这两块。

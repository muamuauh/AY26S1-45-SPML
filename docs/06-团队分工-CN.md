> 文档版本：v2.0 ｜ 生成日期：2026-08-19 ｜ 修订：2026-09-28（按 v3.0 两阶段流程调整职责与排期）

> 团队规模：5 人（本文档使用占位标识 **成员 A–E**，团队确定后替换为真实姓名）

## 0. 使用说明

- 本文档中的 **成员 A–E** 为占位标识。第一次团队会议后，把姓名、联系方式填入 §2 的角色表即可。
- **队长（Team Leader）不预先指定**。若尚未选出，按 §3 的提名标准与选举流程在阶段一启动会议（§10）上产生。
- 分工方案基于文档 `01-技术方案与里程碑-CN.md` 的五层架构与 M0–M7 里程碑（v3.0 两阶段版）；两份文档需同步更新。

## 1. 分工设计原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **按技术层切分，不按周次切分** | 每人拥有一个完整的技术层，端到端负责。避免"这周你做标注、下周他做标注"式的碎片化，责任不清 |
| 2 | **创新模块配双人** | L2 生成层是项目核心创新，单点故障风险太高，必须两人协作（主责 + 副责） |
| 3 | **每人都有一个 🔴 高风险任务** | 参照技术路线图 §6 的成熟度评估，高风险任务分散到不同成员，避免全压一人 |
| 4 | **接口先于实现** | 成员之间的数据格式、接口约定必须在编码前书面确定（见 §6），否则集成阶段必然返工 |
| 5 | **队长不承担最重的技术任务** | 队长需要 20–25% 的时间做协调、对接导师、管进度。若同时背最难的技术模块，两头都做不好 |

## 3. 队长（Team Leader）

### 3.1 队长职责

队长**不是**技术负责人，而是项目协调者。具体职责：

| 类别 | 职责 |
|------|------|
| **对外** | 与导师的唯一对接人；组织并主持每周线下例会；准备汇报材料 |
| **进度** | 维护看板；每周核对里程碑；识别延期并提前预警 |
| **决策** | 主持决策门会议（TGB、TG2–TG5）；组织降级路径的评估与表决 |
| **协调** | 处理成员之间的接口争议；调配临时人力支援落后模块 |
| **文档** | 保证会议纪要、决策记录、贡献记录及时入库 |
| **仲裁** | 技术分歧无法达成一致时组织表决；分工冲突时做最终裁定 |

**时间占比**：约 20–25% 用于协调工作，因此队长承担的技术模块应是五个角色中相对较轻的一个。

### 3.2 提名标准

候选人应满足以下条件。**加粗项为必要条件**，其余为加分项。

| # | 标准 | 说明 | 权重 |
|---|------|------|------|
| 1 | **能保证线下出勤** | 项目明确要求 `regular in-person meetings on campus`，且 `absence and remote working are unacceptable`。无法稳定到校者不具备候选资格 | **必要** |
| 2 | **时间投入可保证** | 项目要求 `substantial time commitment`；队长额外承担 20–25% 协调工作 | **必要** |
| 3 | **沟通与协调意愿** | 愿意主动追进度、处理分歧，而非只想埋头写代码 | **必要** |
| 4 | 项目管理经验 | 有带队或组织经验者优先 | 高 |
| 5 | 技术全局理解 | 能理解五个技术层的相互依赖，而非只懂自己那块 | 高 |
| 6 | 书面表达能力 | 需撰写汇报材料、会议纪要、与导师的书面沟通 | 中 |
| 7 | 冲突处理能力 | 能在分歧中保持中立并推动决策 | 中 |

> **重要提醒**：标准 1（线下出勤）是项目简介明文规定的硬性要求，措辞为 `absence and remote working on the project are unacceptable`。选举前请所有候选人先确认自己能满足这一条。

### 3.3 选举流程

若队长尚未选出，在**阶段一启动会议**（§10）上完成：

```
Step 1  宣读职责与标准（5 分钟）
        全体成员阅读 §3.1 与 §3.2，确认理解

Step 2  自荐 / 他荐（10 分钟）
        · 自荐：有意愿者说明自己符合哪些标准
        · 他荐：可提名他人，被提名者需当场表态是否接受
        · 每位候选人陈述 2 分钟：为什么是我、我打算怎么管进度

Step 3  资格确认（5 分钟）
        逐一核对候选人是否满足三项必要条件（1/2/3）
        任一不满足者退出候选

Step 4  无记名投票（5 分钟）
        · 每人一票，可投给自己
        · 获票最多者当选
        · 平票：进行第二轮，仅在平票者之间投票
        · 第二轮仍平票：由导师裁定

Step 5  确认与记录（5 分钟）
        · 当选者当场确认接受
        · 记入会议纪要，更新本文档 §2.1 角色表
        · 同步告知导师
```

### 3.4 任期与更换

| 项 | 规定 |
|----|------|
| 任期 | 全项目周期（W1–W16） |
| 中期复核 | **W8（项目中点）做一次匿名满意度复核**，5 分制，低于 3.0 触发讨论 |
| 更换条件 | 满足以下任一：① 队长主动请辞；② 超过半数成员书面提出更换；③ 连续两周未履行核心职责（未组织例会、未维护看板） |
| 更换流程 | 重新执行 §3.3 的 Step 2–5 |
| 副队长 | 建议同时推选一名副队长（得票第二者），在队长缺席时代行职责 |

### 5.2 阶段一人力安排建议

- **A**：W4 完成类别映射表后，协助 C、D 核验数据质量
- **B**：W4–W7 做生成环境预研（不在阶段一关键路径上，但决定阶段二能否按时开工）
- **E**：W4 末前交付接口 I5（感知输出 schema），规则层用假检测结果与 baseline 训练并行开发
- **M3（W8–W10）期间 C、D 负载较低**：支援 B 做 G4 人工抽检，并提前准备 E7 鲁棒性测试集

## 7. 协作机制

### 7.1 会议节奏

| 会议 | 频率 | 时长 | 形式 | 主持 | 产出 |
|------|------|------|------|------|------|
| **周例会** | 每周 1 次 | 60 分钟 | ⚠️ **必须线下（项目硬性要求）** | 队长 | 会议纪要入库 |
| 技术对齐会 | 按需 | 30–60 分钟 | 线下优先 | 发起人 | 决议记录 |
| **决策门会议** | 5 次（TGB、TG2–TG5） | 90 分钟 | ⚠️ **必须线下 + 导师参与** | 队长 | 决策记录 + 是否触发降级 |
| 日常同步 | 每日 | 异步 | 群消息 / Issue | — | 阻塞项当天暴露 |

**周例会固定议程**：
```
1. 上周完成情况对照（10 min）—— 逐人 2 分钟
2. 本周计划与依赖声明（15 min）—— 明确"我需要谁在什么时候给我什么"
3. 阻塞项与求助（15 min）
4. 里程碑与关键路径检查（10 min）—— 队长主持
5. 决议与行动项确认（10 min）—— 每项行动明确责任人与截止时间
```

> ⚠️ **关于线下要求**：项目简介明确写明 `regular in-person meetings and discussions on campus are required`，且 `absence and remote working on the project are unacceptable`。建议固定每周会议的时间与地点，并全员确认可出席，写入会议纪要作为承诺记录。

### 7.2 代码协作规范

| 项 | 约定 |
|----|------|
| 仓库 | https://github.com/muamuauh/AY26S1-45-SPML |
| 分支策略 | `main` 保护；每人在 `feat/<模块名>` 分支开发；通过 PR 合入 |
| PR 规则 | 至少 1 人 Review；关联对应的 Issue；CI 通过（如已配置） |
| 提交规范 | `<type>: <描述>`，type ∈ {feat, fix, docs, exp, refactor, chore} |
| 大文件 | 数据与模型权重**不入 Git**，用 DVC 管理（`.gitignore` 已配置） |
| 实验记录 | 每次实验必须在 W&B 留痕，run 名含分支名与关键超参 |

### 7.3 升级机制（Escalation）

```
问题出现
   │
   ├─ 技术问题，自己 4 小时内无进展
   │     → 群里 @ 相关成员求助
   │
   ├─ 跨模块依赖阻塞，超过 1 天
   │     → 报告队长，队长协调优先级
   │
   ├─ 里程碑预计延期超过 3 天
   │     → 队长在周例会提出，全队评估是否触发降级路径
   │
   └─ 决策门未通过 / 成员长期缺席 / 无法解决的分歧
         → 队长上报导师
```

## 8. 贡献记录与公平性

小组项目最常见的矛盾是"贡献说不清"。建议从第一周就建立可追溯的记录，而不是等到最后互相举证。

| 记录方式 | 内容 | 维护者 |
|---------|------|--------|
| Git 提交历史 | 代码贡献，天然可追溯 | 自动 |
| PR 与 Review 记录 | 谁写的、谁审的 | 自动 |
| 会议纪要的行动项 | 每项任务的责任人与完成情况 | 队长 |
| 实验记录（W&B） | 谁跑了哪些实验 | 自动 |
| 文档章节署名 | 论文/报告每章的执笔人 | 队长汇总 |
| **月度贡献自述** | 每人 W4 / W8 / W12 / W16 各写一段 200 字工作小结 | 各成员 |

> **建议**：在最终报告中附一张**贡献声明表**（Contribution Statement），列明每人负责的模块与主要产出。这是学术论文的通行做法（CRediT taxonomy），也能有效避免评分争议。

## 9. 应急预案

| 情况 | 应对 |
|------|------|
| **某成员长期缺席（> 2 周）** | ① 队长先私下沟通了解原因 ② 无法恢复则上报导师 ③ 其职责按 §9 表重新分配 |
| **某成员进度严重落后** | 周例会公开评估；由队长调配临时支援；必要时缩减其模块范围 |
| **队长无法履职** | 副队长接管；按 §3.4 重新选举 |
| **关键成员（B）离队** | B 的生成模块由 A 接手（A 本就是副责）；同时触发降级路径 D2 简化生成路线 |
| **两人以上同时缺席** | 立即上报导师，重新评估项目范围（大概率触发 D8） |

### 成员缺失时的职责再分配预案

| 缺失成员 | 职责接管方案 | 触发的降级 |
|---------|------------|-----------|
| A（数据） | Taxonomy 与类别映射 → 队长 + D；数据维护 → C、D 分摊 | —（数据整编已完成） |
| B（生成） | 生成 → A 接手（副责）；闸门 → E | **D2**（只保留 Inpainting 路线） |
| C（感知-人） | Workers → D 接手；行为识别 → 直接放弃 | **D6**（单帧姿态替代） |
| D（感知-景） | Machinery → C 接手；Terrain/Materials → 放弃 | **D8**（降为两维） |
| E（融合系统） | 规则与 Demo → C 接手；融合 → 队长 + C；系统 → 简化为脚本 | **DB / D4 + D5** |

> 这张表的意义不是"预期有人会走"，而是让团队清楚：**每个角色的不可替代性有多高**。B 和 E 的缺失代价最大，因此这两个角色更需要有人能"看得懂"其代码——建议 PR Review 时刻意让另一人审这两块。

## 一、系统总体架构

TelecomSafe 采用 **五层架构**，每层职责单一、可独立评估、可独立分工。

```
┌──────────────────────────────────────────────────────────────┐
│  L5  应用层  Application                                      │
│      风险报告生成 / Web 可视化面板 / 告警推送 / 案例检索         │
└──────────────────────────────────────────────────────────────┘
                              ▲
┌──────────────────────────────────────────────────────────────┐
│  L4  融合与决策层  Fusion & Decision                           │
│      四维证据对齐 → 规则约束 → 风险评分 → 等级判定 → 可解释输出   │
└──────────────────────────────────────────────────────────────┘
                              ▲
┌──────────────────────────────────────────────────────────────┐
│  L3  感知层  Perception  (四个并行分支)                         │
│   ┌──────────┬──────────┬──────────┬─────────────────────┐  │
│   │ Terrain  │ Machinery│ Materials│ Workers             │  │
│   │ 语义分割 │ 检测+状态│ 检测+堆叠│ 检测+PPE属性+动作    │  │
│   └──────────┴──────────┴──────────┴─────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
                              ▲
┌──────────────────────────────────────────────────────────────┐
│  L2  数据层  Data   ★项目核心创新★                             │
│    公开数据整编/标注 ── 生成式增广 Pipeline ── 质量筛选闸门     │
└──────────────────────────────────────────────────────────────┘
                              ▲
┌──────────────────────────────────────────────────────────────┐
│  L1  输入层  Input                                            │
│      固定摄像头 / 手持照片 / UAV 航拍 / 塔上作业记录仪           │
└──────────────────────────────────────────────────────────────┘
```

## 二、分层技术选型

### L1 输入层

| 输入源 | 场景 | 说明 |
|--------|------|------|
| 手持照片 | 巡检拍照、隐患上报 | **优先支持**，最容易获取，MVP 从此入手 |
| 固定摄像头 | 基站围栏、机房出入口 | 支持视频流，用于行为识别 |
| UAV 航拍 | 塔架整体、场地地形 | 视角特殊，需专门数据（见 AIDCON 数据集） |
| 塔上记录仪 | 高空作业 PPE / 安全带 | 电信行业**最具特色**的输入源，差异化亮点 |

> **建议**：MVP 阶段只做「手持照片 + 固定摄像头」，UAV 与塔上记录仪作为扩展项，避免战线过长。

### L2 数据层（详见 `03-生成式数据增广Pipeline设计-CN.md`）

| 组件 | 技术选型 | 备选 |
|------|---------|------|
| 基础生成模型 | **SDXL / Stable Diffusion 3.5** | FLUX.1-dev（质量更好但显存要求高） |
| 领域适配 | **LoRA 微调**（种子数据 200–500 张） | DreamBooth（数据更少但易过拟合） |
| 布局可控生成 | **ControlNet**（Canny / Depth / OpenPose / Seg） | GLIGEN、T2I-Adapter |
| 局部编辑 | **SD Inpainting + SAM 掩码** | Paint-by-Example |
| 自动标注 | **Grounding DINO + SAM 2** | ControlNet-Seg 路线生成时即知布局，标注零成本 |
| 质量闸门 | CLIP-Score + FID + 检测器置信度 + 人工抽检 | 结构/外观联合度量 |

### L3 感知层

| 分支 | 任务 | 推荐模型 | 输出 |
|------|------|---------|------|
| **Terrain** | 语义分割 | SegFormer-B2 / SAM 2 + 轻量分类头 | 地面类别掩码（平整/坑洼/积水/沟槽/斜坡） |
| **Machinery** | 检测 + 状态 | YOLOv11 / RT-DETRv2 | 机械框 + 类别 + 作业状态 + 与人距离 |
| **Materials** | 检测 + 关系 | YOLOv11 + 堆叠几何规则 | 材料框 + 堆放高度比 + 是否越界 |
| **Workers** | 检测 + 属性 | YOLOv11-pose + 多标签 PPE 头 | 人框 + 关键点 + PPE 状态向量 |
| **Behaviour** | 动作识别 | **ST-GCN++**（骨架流，抗低分辨率）+ VideoMAE-v2（RGB 流） | 动作类别 + 置信度 |

> **关键设计决策**：Workers 分支采用 **共享主干 + 多头** 结构（检测头 + 姿态头 + PPE 多标签头），避免三个独立模型带来的推理开销与结果不一致。

### L4 融合与决策层 ★ 学术贡献的第二个落点 ★

**不要做简单加权求和。** 推荐 **三级分层融合**：

```
第 1 级｜实体级融合 (Entity-level)
  · 空间对齐：同一图像坐标系下关联 人-机-料-地
  · 输出实体图 G = (V, E)，V = 检测实体，E = 空间/交互关系
      例：worker_1 --[距离 1.2m]--> excavator_1
          worker_2 --[站立于]--> terrain_uneven_3

第 2 级｜规则约束层 (Rule Layer)
  · 将安全规范编码为可判定谓词（OSHA 1926 / GB 26859 / 运营商作业规程）
      R1: 高空作业(h>2m) ∧ ¬安全带    → 严重违规 (w=1.0)
      R2: 人-机距离 < 安全半径        → 高风险   (w=0.8)
      R3: 材料堆高 > 1.8m ∧ 无固定    → 中风险   (w=0.5)
      R4: 坑槽边缘 1m 内有人 ∧ 无护栏 → 高风险   (w=0.8)
  · 优点：可解释、可审计、可对齐法规 —— 这是打动评审的关键

第 3 级｜可学习融合 (Learnable Fusion)
  · 用 GNN（在实体图 G 上）或注意力网络学习规则权重与交互项
  · 处理规则覆盖不到的复合风险
  · 输出：场景风险分数 s ∈ [0,1] + 各风险源贡献度（可解释性）
```

**风险等级映射**：`s < 0.3` 低 ｜ `0.3 ≤ s < 0.6` 中 ｜ `0.6 ≤ s < 0.85` 高 ｜ `s ≥ 0.85` 严重

### L5 应用层

- **Web 演示面板**：上传图片/视频 → 四维检测叠加可视化 → 风险评分卡 → 触发规则列表
- **技术栈建议**：FastAPI（后端）+ Gradio 或 React（前端）；模型服务用 ONNX Runtime / TensorRT
- **风险报告**：可接入视觉语言模型（如 Qwen2.5-VL）生成自然语言隐患描述与整改建议 —— 低成本、高展示价值

## 三、评估方案

### 3.1 核心实验矩阵（必做）

| 编号 | 实验 | 目的 | 关键指标 |
|------|------|------|---------|
| E1 | 真实数据 baseline | 建立基线 | mAP@50, mAP@50-95 |
| E2 | + 传统增广（flip/crop/Mosaic/HSV） | 排除"随便加数据就涨"的质疑 | Δ mAP vs E1 |
| E3 | **+ 生成式增广（本方法）** | **核心贡献验证** | Δ mAP vs E2 |
| E4 | 纯合成训练 → 真实测试 | 量化域间隙（sim-to-real gap） | mAP 保持率 |
| E5 | 合成/真实配比扫描（0/25/50/100/200%） | 找最优配比，画曲线 | mAP-ratio 曲线 |
| E6 | 长尾类别专项 | 证明对稀有风险类别提升更大 | 稀有类 AP 提升 |
| E7 | 鲁棒性测试 | 对应原文 robustness 要求 | 低光/雨雾/模糊/小目标下 mAP 衰减率 |
| E8 | 融合模块消融 | 验证 L4 设计 | 风险等级 Accuracy / Macro-F1 / Kappa |
| E9 | 跨站点泛化 | 训练站点 A → 测试站点 B | mAP 跨域下降幅度 |

> **E3 与 E6 是论文的两张王牌**：生成式增广对**稀有危险类别**（真实数据里几乎拍不到的场景）提升最显著，这是最有说服力的证据。

### 3.2 评估指标定义

| 层级 | 指标 |
|------|------|
| 检测 | mAP@50, mAP@50-95, Precision, Recall, FPS |
| 分割 | mIoU, Pixel Accuracy |
| 属性/行为 | Multi-label F1, Top-1 Accuracy, 混淆矩阵 |
| 生成质量 | FID, KID, CLIP-Score, 人工真实性评分（5 分制，≥3 名评分者，报告评分者一致性 Kappa） |
| 融合决策 | 风险等级 Accuracy, Macro-F1, Cohen Kappa（对照安全专家标注） |
| 系统 | 端到端延迟, 显存占用, 模型体积 |

### 3.3 基线对比对象

- 通用检测器：YOLOv8/v11、RT-DETR（无领域适配）
- 现有 PPE 检测公开方案（CHV / SHEL5K 上的已发表结果）
- 商用产品的公开指标（如可获得）
- 生成增广既有工作：Kim & Yi (2024)、Lee et al. (2025) 的报告数值（见文献综述）

## 四、里程碑计划

以 **16 周**（一学期）为基准；若为 12 周，压缩 M2/M5，并把 UAV 与视频行为识别降级为可选。

### 阶段总览

| 阶段 | 周次 | 名称 | 关键交付物 |
|------|------|------|-----------|
| M0 | W1 | 立项与调研 | 需求文档、文献综述、分工表 |
| M1 | W2–W3 | 数据基建 | 种子数据集 + 标注规范 + 风险分类体系 |
| M2 | W4–W6 | 生成 Pipeline | 微调生成模型 + 合成数据 v1 + 质量报告 |
| M3 | W7–W9 | 感知模型 | 四分支模型 + E1/E2/E3 实验结果 |
| M4 | W10–W11 | 融合与决策 | 规则库 + 融合模块 + E8 结果 |
| M5 | W12–W13 | 系统集成 | 可运行 Demo 系统 |
| M6 | W14–W15 | 完整评估 | E4–E9 全实验 + 消融表 |
| M7 | W16 | 交付 | 论文/报告 + 答辩 PPT + 代码仓库 |

### 详细里程碑

#### M0｜W1 立项与调研
- [ ] 确定电信施工**风险分类体系（Risk Taxonomy）**——最重要的第一步，后续所有标注/生成/评估都依赖它
- [ ] 完成文献综述初稿（见 `04-文献综述-CN.md`）
- [ ] 明确分工与协作规范（Git + DVC + 实验记录用 Weights & Biases 或 MLflow）
- [ ] **交付**：Risk Taxonomy v1.0（建议 4 大类 × 20–30 个细类）

#### M1｜W2–W3 数据基建
- [ ] 下载并统一格式化公开数据集（SODA / MOCS / CHV / SHEL5K，详见文档 02）
- [ ] **T2 社区数据集**：下载 Roboflow Universe 电信塔集、safety harness 系列、Kaggle 施工安全集（含 NO-Hardhat 负类）
- [ ] **T3 开放许可整编**：在 Openverse / Wikimedia Commons 检索并人工筛选电信场景图像 **200–500 张**，同步建立 `licence_manifest.csv` 记录来源与署名
- [ ] ❌ ~~实地采集~~ —— v2.0 已取消，本项目不做任何现场采集
- [ ] 制定**标注规范文档**（含边界情况判定标准，避免多人标注不一致）
- [ ] 标注种子数据 **≥200 张**（用 Label Studio / CVAT；先用 Grounding DINO 预标注再人工修正，可省约 60% 工时）
- [ ] 🔒 划出 **TelecomEval 测试集（150–300 张真实图像）并冻结** —— 绝不参与 LoRA 微调，绝不参与生成条件构建
- [ ] **交付**：TelecomSeed-v1 + TelecomEval-v1 + 标注规范 + `licence_manifest.csv`

#### M2｜W4–W6 生成 Pipeline ★核心★
- [ ] 基础模型选型对比实验（SDXL vs SD3.5 vs FLUX，小规模试跑）
- [ ] LoRA 微调注入电信施工领域特征
- [ ] 实现 4 条生成路线：文生图 / ControlNet 布局控制 / Inpainting 编辑 / 背景替换
- [ ] 实现质量筛选闸门（CLIP + FID + 检测器过滤）
- [ ] 生成合成数据 **≥3000 张**，记录通过闸门后的保留率
- [ ] **交付**：TelecomSynth-v1 + 生成质量评估报告
- [ ] ⚠️ **风险检查点**：若 FID > 60 或人工真实性评分 < 3.0，立刻回退调整，不要带病进入 M3

#### M3｜W7–W9 感知模型
- [ ] 四分支模型训练（可先做 Workers + Machinery 两个高价值分支）
- [ ] 完成 E1 / E2 / E3 实验 —— **项目成败的关键节点**
- [ ] Workers 分支多头结构实现与调优
- [ ] **交付**：模型权重 + E1–E3 对比表
- [ ] ⚠️ **决策点**：若 E3 相对 E2 提升 < 2 mAP，需诊断原因（生成质量？配比？类别选择？）并调整，而非硬推进

#### M4｜W10–W11 融合与决策
- [ ] 编码安全规则库（≥15 条可判定规则，标注法规出处）
- [ ] 实现实体图构建 + 三级融合
- [ ] 邀请 2–3 名安全专家（或按规范人工标注）对 200 张测试图打风险等级，作为融合模块 ground truth
- [ ] 完成 E8 实验
- [ ] **交付**：融合模块 + 风险规则库文档

#### M5｜W12–W13 系统集成
- [ ] 端到端推理 pipeline 打通
- [ ] Web Demo 界面（上传 → 可视化 → 评分卡 → 规则列表）
- [ ] 模型导出与加速（ONNX / TensorRT）
- [ ] **交付**：可运行的 TelecomSafe Demo

#### M6｜W14–W15 完整评估
- [ ] 完成 E4–E9 全部实验
- [ ] 鲁棒性测试集构建（人工加噪：低光、雨雾、运动模糊、遮挡、小目标）

## 五、风险登记表（Risk Register）

| ID | 风险 | 概率 | 影响 | 缓解措施 | 触发阈值 |
|----|------|------|------|---------|---------|
| R1 | 电信真实数据不足（**已取消现场采集**，全部依赖公开来源） | 高 | 高 | T1 学术数据集迁移 + T2 社区专项集 + T3 开放许可图像整编；量本就有限，因此更依赖 T4 生成式补齐。必要时降级为"高处作业/塔架类"泛化场景（D1） | W3 末 TelecomSeed < 150 张 |
| R2 | 生成图像质量不达标，负迁移 | 中 | 高 | 严格质量闸门；保守配比（先 25%）；保留纯真实 baseline | FID > 60 或 E3 低于 E2 |
| R3 | 算力不足（扩散模型训练成本高） | 中 | 中 | 用 LoRA 而非全量微调；SDXL-Turbo 加速；租用云 GPU；分批生成 | 单卡 < 16GB |
| R4 | 行为识别缺视频数据 | 高 | 中 | **降级方案**：用单帧姿态 + 规则判定替代视频动作识别 | W9 末无可用视频数据 |
| R5 | 融合模块缺 ground truth | 中 | 中 | 用规则库自动生成弱标签 + 少量专家标注校准 | W10 |
| R6 | 团队协作/进度失衡 | 中 | 中 | 每周线下例会（项目硬性要求）+ 看板 + 代码 Review | 任一里程碑延期 > 1 周 |
| R7 | 范围蔓延（四维全做太重） | 高 | 高 | MVP 优先 Workers + Machinery；Terrain/Materials 做简化版 | W7 |

> **最重要的一条是 R7**。四个维度全做到高质量在一学期内几乎不可能。**建议在 M0 就明确「主攻 Workers + Machinery，Terrain 与 Materials 做到可用即可」**，并在报告中诚实说明范围界定。

## 七、写作与展示建议

### ⚠️ 重要更正：学校报告模板不是学术论文结构

本节 v1.0 曾建议按学术论文结构（Introduction / Related Work / Method / Experiments / Conclusion）撰写。**核对学校官方模板 `template/EE6008-Project ReportTemplate.docx` 后发现，EE6008 的项目报告是「项目管理报告」，不是学术论文。**

两者差异很大，必须以官方模板为准：

| 学术论文（原建议） | EE6008 官方报告模板 |
|------------------|-------------------|
| Introduction | 1. Purpose / Project Objectives |
| **Related Work（独立章节）** | ❌ **没有独立的文献综述章节** |
| Method（多个技术章节） | 2. Project Summary（合并为一章） |
| Experiments | 并入 2. Project Summary 与 6. Outcomes / Benefits |
| — | 3. Scope（含交付物、活动、**范围变更说明**） |
| — | 4. Schedule（计划 vs **实际**里程碑日期） |
| — | 5. Cost（计划 vs 实际成本） |
| Discussion & Limitations | 并入 6. Outcomes / Benefits |
| — | 7. **Individual Reports from Team Members**（每人独立撰写 + 反思） |
| References | 8. References |
| — | Appendix — Project Members Information（贡献表） |

**三个最关键的差异**：

1. **没有 Related Work 章节** —— 文档 04 的文献综述内容不能整段照搬。应压缩后放入 §1 Purpose/Objectives 作为立项依据，参考文献列入 §8 References。
2. **要求「计划 vs 实际」对照** —— §4 Schedule 与 §5 Cost 都有「Planned」和「Actual」两列。**这意味着项目全程必须记录实际完成日期**，不能到最后补。建议从 M0 就在看板里记录每个里程碑的实际完成日。
3. **每人必须写个人报告与反思** —— §7 是个人独立撰写的，包含「学到的工程知识、问题分析、方案设计、想分享的内容」。这部分无法代笔，也直接影响个人评分。

按官方模板的 8 节 + 附录组织，每节标注内容来源：

### 7.3 §7 Individual Reports 撰写指引

模板要求每位成员覆盖以下四点。这部分**必须本人撰写**，是个人评分的直接依据：

| 模板要求 | 建议写法 | 可引用的材料 |
|---------|---------|------------|
| Engineering knowledge learned | 具体到技术点，不要泛泛而谈。例："通过 LoRA 微调理解了低秩适配如何在 500 张样本上避免过拟合" | 自己负责的模块 |
| Problem Analysis | 描述一个你实际遇到并分析的问题。例："发现合成图像中提示词不遵从现象，通过 CLIP-Score 定位到 15% 的语义不一致样本" | 失败模式表（文档 03 §11） |
| Design/development of solutions | 你设计的方案与取舍。例："选择 Inpainting 而非 T2I 路线，因为标注可继承且域间隙更小" | 技术选型依据（文档 [02](02-数据集与预训练模型调研-CN.md)）与降级路径（文档 [05 §4](05-技术路线图-CN.md)） |
| Anything to share | 协作经验、时间管理、对项目的反思 | 个人月度贡献自述（文档 06 §8） |

> **建议**：每人在 W4 / W8 / W12 / W16 各写一段 200 字工作小结（文档 06 §8 已建议），到 M7 时把四段整理成个人报告即可，避免最后回忆不起来。

### 7.4 全程需要记录的内容（否则最后补不出来）

官方模板要求「计划 vs 实际」对照与个人贡献说明，这些**必须在项目进行中就记录**：

```
□ 每个里程碑的实际完成日期        → §4 Schedule 的 Actual 列
□ 每次触发降级路径的时间与原因     → §3 Scope 的 Changes 部分
□ 实际发生的成本（如云 GPU 费用）  → §5 Cost 的 Actual 列
□ 每人负责的模块与主要产出        → §7 + Appendix
□ 每人撰写的报告章节与页码        → Appendix 的 Report Contribution 列
□ 每周会议纪要与决策记录          → §3 Changes 的证据来源
```

**建议**：在仓库建 `progress/` 目录，用 `milestones.md` 记录实际日期、`changes.md` 记录范围变更，每周例会后由队长更新。

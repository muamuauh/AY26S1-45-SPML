# TelecomEval：进展、待办与类别（2026-10-16）

> **10 月 16 日计划调整：** 改为每位组员用任意方法收集并标注至少 50 张图，见 [TelecomEval-贡献规范-CN.md](../guides/TelecomEval-贡献规范-CN.md)。下文提到的筛选、标注、收集任务包已撤回；本页保留作背景说明和类别定义。

> English version: [TelecomEval-Status-EN.md](TelecomEval-Status-EN.md)

TelecomEval 是我们的**真实电信场景测试集**，只回答一个问题：检测器在电信现场表现如何？电信现场包括铁塔、屋顶天线、路边机柜、线缆沟槽、人井和电线杆。baseline 只用工地数据训练过，而 TGB 会议（W7，10 月 19 日那一周）和第二阶段的 TG3（E3 必须比 E2 高至少 2.0 mAP）都以这个测试集为准。**冻结之后不再改动。**

## 1. 当前进展

流程是：收集候选图 → 人工筛选 → 用 E2 模型预标注 → 在 Label Studio 里标注 → 导入标注 → 冻结 → 评测。每张图的许可和署名都记录在清单里。

| 步骤 | 状态 |
|---|---|
| **第一轮收集**（Openverse、Wikimedia Commons、CC 许可的 YouTube 视频截图） | 已完成：1,930 张候选图 |
| **第一轮筛选** | 已完成：**保留 167 张（电信 95 + 相邻领域 72）**。相邻领域指电力线路作业，比如线杆、斗臂车，攀爬和安全带的风险与电信相同，单独作为子集报告 |
| **第一轮的问题** | 很多是低分辨率的视频截图，场景和工人也比较单一，不适合直接使用 |
| **第二轮收集**（10 月 14 日） | 已完成：**新增 1,700 张公有领域照片**，来自美国国防部图片库 DVIDS 搬到 Wikimedia Commons 上的图。大多是 1280 × 853 或更大，场景更多样 |
| **第二轮自动打分** | 已完成。**486 张**有人且像作业场景：线缆 / 光纤作业 203、机柜 62、屋顶天线 61、铁塔 52、线杆 31、斗臂车 28、沟槽 20、人井 16。另有 284 张被自动排除（没有人，也不像作业场景） |
| **第二轮人工筛选** | **尚未开始** |
| 预标注、标注、冻结、评测 | 最终版都还没开始，工具都已就绪（见第 2 节） |

**考虑过但放弃的方案：**
- **用生图模型生成测试集**（如 GPT Image）：测到的是模型在 AI 生成图上的表现，而不是真实现场。第二阶段也用生成图训练，TG3 的对比会因此偏向 E3。生成图仍需人工标注，因为用 E2 自动标注就成了拿 E2 自己的答案给 E2 打分。
- **现成的公开数据集：** 没有一个同时包含电信场景、工人和 PPE 标注。
  - 最接近的是天池广东电网高空作业数据集，但学术使用的许可不明确，标签也和我们的不同。
  - 我们检查过的 Roboflow “construction safety v2” 是拼图增广过的，图片被拉伸到 640 × 640，还和训练集（Construction Site Safety）重复，不能用。
- **从其他工地数据集各抽一部分混入 TelecomEval：** 测到的主要是工地上的表现，而验证集已经测过了。可以另做一个跨数据集评测集作为补充，单独报告，例如用训练中没用过的 CHV 和 SHEL5K。

## 2. 待办事项

1. **筛选第二轮的 1,700 张候选图**：在浏览器筛选页里操作，按 1 = 电信、2 = 相邻领域、X = 排除。图片按分数从高到低排，有用的基本都在前 500 张左右。
2. **用同样更严的标准重新筛第一轮的 167 张**（见第 3 节），去掉质量差的。
3. **平衡最终的测试集**：目标是**电信图至少 150 张（理想 200 张）**，另加相邻领域子集，并尽量覆盖各种场景。DVIDS 常有同一次活动的一组几乎相同的照片，每组最多留 2–3 张。
4. **用 E2 预标注**保留下来的图（车辆由 COCO 模型补充）：

   ```
   python -m telecomsafe.data.pseudo_label --weights runs/phase1/e2/weights/best.pt --images data/raw/t3_candidates/images --yolo-out data/raw/t3_candidates/prelabels
   ```

5. **生成标注包**：`python -m telecomsafe.data.package annotate`。包里有 Windows 和 macOS 的一键启动脚本。
6. **在 Label Studio 里标注**：按标注规范和第 4 节的类别表来标。约 10% 的图由第二个人复核。
7. **导入标注并冻结：**

   ```
   python -m telecomsafe.data.package intake-annotations <annotations.json>
   python -m telecomsafe.data.freeze_eval --create
   ```

   冻结前先看一遍导入时生成的抽检图。
8. **评测**：用 `python -m telecomsafe.evaluate` 评测 E1 和 E2 的 3 个种子，电信和相邻领域分开报告，然后更新第二阶段要针对的弱类清单。
9. **TGB 前来不及时**：先用第一轮的 167 张做一次 “v0” 评测并写明局限，最终版要在第二阶段做任何对比之前冻结。

**工时估算：**

| 任务 | 时间 |
|---|---|
| 筛选 | 1.5–2 小时 |
| 重新筛选 167 张 | 约 0.5 小时 |
| 标注 200 张（修正预标注，每张约 1.5–2 分钟） | 4–6 小时 |
| 导入、冻结和评测 | 约 1 小时 |

筛选和标注都可以按图片编号范围分给多人。

## 3. 筛选标准（比第一轮更严）

**保留**（算电信；电力线路作业算相邻领域）：
- 有人在**室外**真正对电信设施作业：爬铁塔或线杆、安装天线或卫星天线、在路边机柜作业、在沟槽或人井里拉线或熔接光纤。
- 图片**清晰**：照片短边至少 1000 像素，至少有一名工人身高约 80 像素以上。
- 优先选能判断 PPE 的图：安全帽、登高头盔、安全带、反光衣；也包括**没有**佩戴这些的工人，这正是我们最缺的样本。

**排除：**
- 室内办公室、实验室、帐篷和机库。
- 摆拍的合影、仪式和人像。
- 示意图、截图和插画。
- 画面里没有人在作业。
- 和已保留的图几乎一样。
- 纯军事场景（作战装备、武器、军车），且没有电信作业。

## 4. 类别（第一阶段，共 8 类）

以 `configs/taxonomy.yaml` 为准，标注包里的标注规范与它一致。

| 类别 | 框什么 | 判定标准 |
|---|---|---|
| `person` 人员 | 整个人可见的部分 | 身体可见部分超过一半才标；小到认不出是人的不标 |
| `helmet` 安全帽 | 戴在头上的安全帽 | 放在地上、拿在手里的不标 |
| `no_helmet` 未戴安全帽 | **没有**戴安全帽的头部 | 戴普通帽子、头巾、兜帽都算 `no_helmet` |
| `vest` 反光衣 | 穿着的反光背心或高可视性工作服（上身） | 只有带反光条的才算 |
| `no_vest` 未穿反光衣 | 没穿反光衣的人的躯干 | 普通彩色衣服算 `no_vest` |
| `harness` 安全带 | 穿在身上的全身式安全带（肩带、胸带、腿带） | 挂在结构上的绳子和挂钩不标；没系安全带不画框 |
| `machinery` 工程机械 | 机械整体，包括臂架和铲斗 | 挖掘机、吊车、装载机，以及**斗臂车、高空作业平台、放线车、电缆盘拖车** |
| `vehicle` 普通车辆 | 车辆整体 | 普通轿车、皮卡、面包车和普通货车 |

**一致性规则**（风险规则依赖这些规则）：
- 每个能看到头部的人，必须且只能标**一个** `helmet` 或 `no_helmet`。
- 每个能看到躯干的人，必须且只能标**一个** `vest` 或 `no_vest`。
- 铁塔、电线杆、天线本身都**不标**。类别表里有一个 `tower` 类，但第一阶段不启用，留给可选的铁塔规则 R3。

**当前的弱类**（验证集，E2）：`vehicle`（AP50 0.40）和 `no_helmet`（0.42），其余类别都在 0.80 以上。TelecomEval 会告诉我们，到了电信现场这个情况会不会变。

## 5. 需要组员一起定的问题

1. **DVIDS 照片里的军用头盔和迷彩服：** 作战头盔算不算 `helmet`？它是防护头盔，但不是安全帽。迷彩服是否直接算 `no_vest`？这些要在开始标注前定下来。在定下来之前，优先选戴安全帽或登高头盔的图。
2. **相邻领域子集的规模：** 相邻领域的图算不算进 150 张的目标，还是严格分开？目前的计划是分开。
3. **谁负责筛选和标注哪些范围**，以及谁做 10% 的复核。

候选图片和筛选页都不在 git 里（`data/` 被忽略），会通过组内共享文件夹分享。
